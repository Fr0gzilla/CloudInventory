# Baseline SQL–ORM — EV07/EV59

## État conservé

Les cinq tables `run`, `asset`, `ipam_record`, `consolidated_asset`, `anomaly` existent dans le SQL et l'ORM. Les colonnes et leurs types, nullabilités, valeurs par défaut, CHECK, clés primaires, FK composites et règles ON DELETE correspondent avant EV07 ; `INTEGER PRIMARY KEY` attribue les identifiants sous SQLite (PK ORM `nullable=True`). `ipam_record.meta_zone TEXT NULL` est déjà présent des deux côtés : ne pas le recréer et préserver ses valeurs. Aucun nom IP ni DNS IPAM n'est unique. Les clés candidates `asset(id, run_id)` et `ipam_record(id, run_id)`, ainsi que `consolidated_asset(asset_id, run_id)`, sont déjà définies.

Index déjà présents des deux côtés : `idx_asset_run(run_id)`, `idx_asset_run_vm(run_id, vm_id)`, `idx_asset_run_name(run_id, vm_name)`, `idx_asset_run_fqdn(run_id, fqdn)`, `idx_asset_run_ip(run_id, ip_reported)`, `idx_asset_run_node(run_id, node)` sur `asset` ; `idx_ipam_run_ip(run_id, ip)`, `idx_ipam_run_dns(run_id, dns_name)` sur `ipam_record` ; `idx_consolidated_run(run_id)`, `idx_consolidated_ipam_run(ipam_record_id, run_id)`, `idx_consolidated_run_match(run_id, match_status)` sur `consolidated_asset` ; `idx_anomaly_run(run_id)`, `idx_anomaly_asset_run(asset_id, run_id)`, `idx_anomaly_ipam_run(ipam_record_id, run_id)` sur `anomaly`.

## Évolution additive et écart temporaire

Le SQL cible ajoute uniquement `ipam_record.custom_fields TEXT NULL` (objet JSON complet, NULL si absent, objet vide distinct, sans valeur par défaut ni CHECK sur les clés libres) et `idx_ipam_run_zone(run_id, meta_zone)` sur `ipam_record` ; la zone déjà stockée sert au filtre limité au run. Aucun autre index ou table n'est créé. L'ORM existant ne contient encore ni cette colonne ni cet index : les ajouter à `IpamRecord` avec les mêmes nom, type et nullabilité, et ajouter l'index dans `__table_args__`. Conserver intégralement les autres colonnes, contraintes et index. La collecte doit sérialiser sans perte l'objet reçu pour chaque observation IPAM, même non rapprochée ; absence ≠ `{}`.

Pour les bases existantes, enregistrer d'abord comme baseline versionnée l'état réel des cinq tables et des quatorze index ci-dessus, sans recréer les tables ni effacer les lignes. Une migration ultérieure ajoute la colonne nullable et l'index ; une base neuve doit produire le même schéma cible via SQL et ORM. Comparer les deux schémas après migration : colonne, index, clés et contraintes doivent coïncider. La structure interne des custom fields reste ouverte (Q8) ; aucune indexation du JSON libre.

## Delta cible v2.2 — ORM non synchronisé

Le SQL cible comporte désormais `run_schedule(id, frequency, enabled, next_at)` et `anomaly_exception(id, code, target, justification, expires_at, author)` ; créer les modèles ORM correspondants. `run` ajoute `current_step INTEGER NULL` (1–7), `completed_steps INTEGER NULL` (0–7), `run_trigger TEXT NULL` (manuel/planifié), `schedule_id INTEGER NULL` FK vers `run_schedule(id)` ON DELETE SET NULL, et `idx_run_schedule(schedule_id)`. Laisser les anciens runs NULL ; l'application fournit la provenance des nouveaux runs. `anomaly` étend `code` à RENAMED, ajoute `tracking_key TEXT NULL`, `state TEXT NOT NULL DEFAULT 'ouverte'`, `state_changed_at TEXT NULL`, `severity TEXT NOT NULL` et les index de suivi `(tracking_key, created_at)` et de tri `(severity)`. Les sept codes sont aussi admis par `anomaly_exception.code` ; dates en TEXT ISO 8601, enabled booléen INTEGER 0/1. Aligner CHECK, FK et index ORM avant de déclarer RG38 satisfait.

Une migration conservatrice doit reconstruire `anomaly` pour étendre son CHECK SQLite, sans perte des lignes ni des FK composites ; les anomalies historiques n'ont pas de sévérité connue (Q10) : ne pas leur attribuer de classe fictive, prévoir explicitement leur classement avant de rendre la colonne NOT NULL. Les nouveaux constats reçoivent leur sévérité selon la configuration applicative. Historique par run inchangé, suivi inter-runs via `tracking_key` (Q9), transitions, exclusions par code/cible/expiration (Q11–Q12), progression après rollback (Q13), fuseau et planification (Q15) à gérer côté application. Aucun code ORM ni migration n'est modifié ici.

## Delta cible v2.3 — migration conservatrice

Le SQL ajoute `asset.virtual_source TEXT NULL` et `ipam_record.ipam_source TEXT NULL` : deux `ALTER TABLE … ADD COLUMN` sur la base v2.2, sans valeur source fabriquée ni fusion des identités homonymes. Créer `auth_origin`, `role`, `permission`, `account`, `role_permission`, `audit` et leurs index selon `schema.sql` ; ne pas reconstruire les tables historiques, ne pas supprimer les runs, observations et anomalies. Les domaines des deux premiers référentiels sont fixes ; les permissions sont extensibles et aucune attribution par défaut n'est justifiée (Q18). L'unicité `(origin_code, username)` qualifie les identités sans assimiler les origines (Q17). Les comptes locaux exigent un hash non vide ; les comptes LDAP/AD imposent NULL. Les traces d'audit portent identité, action, date et cible historiques et persistent après purge des runs ou retrait du compte (FK SET NULL, Q19). Aucun ancien compte ni rôle ne doit être inventé depuis la configuration applicative.

Le SQL v2.3 cible n'est pas encore synchronisé avec l'ORM v2.2 : ajouter les colonnes, référentiels, FK, CHECK et index dans l'ORM avant de prétendre à RG38. Après migration de v2.2, contrôler `PRAGMA foreign_key_check`, `PRAGMA integrity_check`, le maintien des lignes historiques et la comparaison des schémas SQL/ORM. Migration exécutable et classification des anciennes sévérités (Q10) restent à définir avant une mise en production ; aucune durée de rétention d'audit n'est inventée.
